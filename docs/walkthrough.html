one command · real daemon · real tools

From a clean checkout to an approved tool call.

msk opens a semi-graphical terminal app: a pixel wordmark, rounded composer, status chips, dimmed modal layers and live tool cards. Every session runs in a mode — plan, investigate, exploit, harden, or auto routing — which controls both the operating rules and the tools the kernel loads. This is a real run in a project directory: a mock OpenAI-compatible model asked the kernel to execute a command, the TUI paused for approval, and the tool result returned to the same conversation. The agent sees the files in the directory you launched from.

msk opens the TUI mskd auto-starts scripted-demo works offline cwd is the workspace/resume restores a checkpoint modes plan · investigate · exploit · harden · auto
01

Build once, launch with one word.

The Go envd and Rust workspace build together. After that, msk is the entry point; mskd comes up behind it.

terminal
$ cargo build --bins
$ (cd tools/envd && go build -o ../../target/debug/envd ./cmd/envd)
$ target/debug/msk
1

No daemon yet?

msk starts mskd with the local envd, tools directory and a fresh .msk root. The daemon stays up after you quit.

2

No API key?

The first run opens the setup card. Choose scripted-demo and press Enter: it works offline with no model or key. Type a goal or /demo; you get a real tool session. The embedded envd opens the current directory, so ./challenge is visible immediately. Switch later with Ctrl+P.

The provider list distinguishes the offline demo, Chat Completions, Responses and component providers. The service step offers endpoint presets for OpenAI, DeepSeek, OpenRouter, Groq, Together, Ollama and LM Studio; model presets include a custom input; effort is sent as reasoning_effort or reasoning.effort. The final step accepts an API key (masked), and the result is saved as a provider profile. The header shows the active provider / model / effort at all times.

No key, no fake success: if neither a saved profile key nor the daemon's MSK_LLM_API_KEY is available, the setup screen says so and session creation stops with an actionable message instead of spawning a task that immediately fails.
03

One session, one conversation.

Tool calls, results, user turns and agent text share one borderless timeline. The session list opens only on Tab, and the raw event inspector stays out of the way until you ask for it.

What you see

  • ▸ exec … — the agent requested a tool, with compact arguments.
  • ✓ exec … — the result, in green; ✗ marks a failure.
  • ❯ — your messages; agent text is plain, with a live block cursor while streaming.
  • The header shows the goal, a spinner while running, and the model/effort.

What stays available

  • PgUp/PgDn or ↑/↓ scrolls; End follows the newest output.
  • Tab opens the session switcher and rehydrates each history.
  • Ctrl+P → Event inspector shows the raw events for debugging.
  • Ctrl+P → Terminal opens the daemon PTY; Ctrl+Q detaches.

06

Two demos, depending on what you want to see.

One uses a local mock model to show a real tool round trip; the other is entirely offline and shows the scripted session end to end.

Mock model demo

Starts a local OpenAI-compatible mock, a clean daemon, and the TUI.

Windows
./scripts/demo.ps1
Linux / macOS
./scripts/demo.sh

Type exec, press Enter, approve with y. Then try file, secret, flag, board, or spawn.

Offline demo

No mock server, no key, no network. Uses the built-in scripted session.

terminal
target/debug/msk-tui --root .msk/offline --provider scripted-demo
# then type: /demo

The approval modal appears on the first session_exec; approve a few times to watch shell state, the artifact and the close sequence.

Real model instead of the mock

The TUI selects openai automatically when both variables are present:

environment
export MSK_LLM_BASE_URL=https://api.openai.com/v1
export MSK_LLM_MODEL=gpt-5
export MSK_LLM_API_KEY=...
target/debug/msk

Use /provider openai-responses for the Responses API, or /provider scripted-demo to return to the offline demo. Run msk-tui --doctor to check the daemon, envd, tools, model and key.

07

What is happening underneath.

The TUI is a frontend only. It runs in your current directory and speaks the same IPC as mskctl, the web UI, and the eval harness, so the kernel does not know which client is attached.

Daemon

mskd supervises every task, persists events and checkpoints, and serves approvals and the PTY.

Env

envd provides the managed workspace. dev is the default; isolated requires a validated deployment launcher.

History

task.history returns structured events. Selecting a session rehydrates the same timeline, not a truncated transcript.

Replay

Every turn writes JSONL events and a checkpoint. msk-replay inspects them; --provider replay reruns recorded responses.

Approvals

The daemon owns the request and timeout; any attached client can answer. The modal is a view of that queue.

Other clients

msk-web serves the same sessions over a loopback browser UI; mskctl remains the scriptable path.
